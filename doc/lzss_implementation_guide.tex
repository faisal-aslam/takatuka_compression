\section{Goal and Non-Goal}

\textbf{Goal}: an LZSS-style compressor where the dictionary is never stored. The decoder
reconstructs it implicitly, byte by byte, from the same data it has already decoded --
exactly the same way the encoder does. Nothing about a "dictionary" is ever written to
the compressed file; only literal bytes and (length, distance) back-references are.

\textbf{Non-goal}: reproducing DEFLATE. DEFLATE's specific parameters (32KB window,
greedy/lazy matching, static per-block Huffman) were 1996 engineering trade-offs for
speed and memory, not a template for maximum ratio. This guide deliberately departs from
several of them; each departure is called out explicitly.

\begin{tcolorbox}[colback=green!5!white,colframe=green!45!black,title=Running example used throughout this document]
Every worked example below uses the same 13-byte string, so the pieces connect into one
coherent picture instead of thirteen disconnected toy cases:
\[
  S = \texttt{a\,b\,c\,a\,b\,c\,a\,b\,c\,x\,a\,b\,c}, \qquad
  \text{positions } 1,2,\dots,13.
\]
It repeats \texttt{"abc"} three times, is interrupted once by \texttt{"x"}, then repeats
\texttt{"abc"} once more. Small enough to trace completely by hand, rich enough to show
a real match, a real choice between two parses, and a real place where a repeat
distance changes.

All bit costs below use exactly the formulas in \texttt{lzss\_cost.h}: a literal costs 9
bits (1 flag + 8 data bits); a match of length $s$ and distance $\delta$ costs
$1 + \text{var}(s-1) + \text{var}(\delta)$ bits, where $\text{var}(x) = 2\lfloor \log_2
x\rfloor + 1$ is the Elias-gamma-style variable-length code cost. Every number quoted
below was computed with this exact formula (verified by script, not by hand), so you can
recompute any of them yourself as a sanity check while implementing.
\end{tcolorbox}

\section{Why No Header Dictionary Is Needed: The Causality Argument}
\label{sec:causality}

\begin{definition}[Implicit dictionary]
An implicit dictionary at position $l$ is simply the already-decoded prefix
$x_{1..(l-1)}$ of the output itself. There is no separate structure to store or
transmit.
\end{definition}

\begin{theorem}[Decoder can always reconstruct the dictionary on its own]
\label{thm:causal}
If the encoder only ever emits back-references whose source position $p$ satisfies
$p < l$ (the current position), the decoder can resolve every reference using only
bytes it has \emph{already} produced, in the same left-to-right order the encoder used.
No side information about the dictionary is required.
\end{theorem}

\begin{proof}
By induction on $l$. At $l = 1$ nothing has been decoded, so only a literal can be
emitted (there is nothing to reference). Suppose the decoder has correctly reconstructed
$x_{1..(l-1)}$. If the encoder emits a literal at $l$, the decoder appends it directly.
If the encoder emits a back-reference $(s, \delta)$ with source position
$p = l - \delta$, then $p < l \le l$, so $x_p$ (and, byte by byte, $x_p, \dots,
x_{p+s-1}$, even if $p + s - 1 \ge l$, since each output byte becomes available to be
read the instant it is produced) is already in the decoder's output buffer. The decoder
copies it forward exactly as the encoder did. By induction, this holds for all $l$.
\end{proof}

This is the same argument that dissolved the "per-path hash" confusion from earlier in
this project: match validity is a property of the \emph{fixed input string}, not of
which parse/path was chosen to reach a given position. Section~\ref{sec:matchfinder}
turns this into an algorithm for finding valid matches quickly.

\begin{tcolorbox}[colback=green!5!white,colframe=green!45!black,title=Worked example: decoding without a dictionary]
Suppose the encoder emitted, for our running example $S$: three literals \texttt{a},
\texttt{b}, \texttt{c}; then one back-reference $(s{=}6,\delta{=}3)$; then a literal
\texttt{x}; then a back-reference $(s{=}3,\delta{=}4)$. The decoder replays this with no
dictionary at all, just its own output buffer:
\begin{enumerate}
  \item Emit literals \texttt{a}, \texttt{b}, \texttt{c} $\to$ buffer is \texttt{"abc"}.
  \item See $(6,3)$: copy 6 bytes starting 3 bytes back from the current end (position
  $4-3=1$). Copy byte-by-byte: buffer[4] = buffer[1] = \texttt{a}; buffer[5] =
  buffer[2] = \texttt{b}; buffer[6] = buffer[3] = \texttt{c}; buffer[7] = buffer[4]
  (just written!) = \texttt{a}; buffer[8] = buffer[5] = \texttt{b}; buffer[9] =
  buffer[6] = \texttt{c}. Buffer is now \texttt{"abcabcabc"}.
  \item Emit literal \texttt{x} $\to$ \texttt{"abcabcabcx"}.
  \item See $(3,4)$: copy 3 bytes starting 4 back from position 11 (source position 7):
  buffer[11..13] = buffer[7..9] = \texttt{"abc"}. Final buffer:
  \texttt{"abcabcabcxabc"} -- exactly $S$.
\end{enumerate}
Note step 2: the source range (positions 1--6) and the destination range (positions
4--9) \emph{overlap}, yet the byte-by-byte copy still works, because each source byte is
always already-written by the time it's read (Theorem~\ref{thm:causal}'s proof handles
this explicitly). This overlapping-copy trick is exactly how a single short back-reference
can expand into a long run.
\end{tcolorbox}

\begin{tcolorbox}[colback=blue!5!white,colframe=blue!50!black,title=What this replaces]
Your current \texttt{compressed\_header.c} / \texttt{code\_map.c} store an explicit
dictionary. Under the design in this document, those become unnecessary: the header
only needs to store per-block metadata (block length, entropy-coder tables if any), not
a symbol table. This is the single biggest structural simplification in this rewrite.
\end{tcolorbox}

\section{Bounding Memory and Speed: The Sliding Window}
\label{sec:window}

Section~\ref{sec:candidates} already replaces the old \texttt{Graph} structure's memory
cost (which scaled with $O(n\cdot k)$) with something much smaller. This section does
the same thing for the \emph{window} itself: right now, "the window" is implicitly
"everything before position $l$ in the current 64{,}000-byte block" -- a
\emph{growing} dictionary bounded only by block size, not a true sliding window. That's
fine while blocks stay small, but it doesn't give you an explicit, tunable memory
ceiling, and it can't reference across a block boundary. This section fixes both.

\subsection{Search buffer vs.\ look-ahead buffer}

\begin{definition}[Search buffer and look-ahead buffer]
The \emph{search buffer} is the set of already-decoded bytes eligible as copy sources
-- this is your window, and its size is what you want to bound. The \emph{look-ahead
buffer} is just the next few not-yet-encoded bytes the matchfinder is trying to extend
a match into; it only needs to be as large as the longest match you're willing to
consider (Section~\ref{sec:candidates}'s note about not hard-capping match length still
applies -- just cap it at something sane, e.g.\ a few hundred to a few thousand bytes,
not thousands of times the window).
\end{definition}

Only the search buffer needs active memory-bounding; the look-ahead buffer is small and
fixed by construction.

\subsection{A fixed-memory search buffer: the ring buffer}
\label{sec:ringbuffer}

\begin{definition}[Ring-buffer window]
Choose a window size $W$ (a power of two, for cheap modular arithmetic). Store the
search buffer as \texttt{buffer[W]}; the byte at absolute stream position $i$ lives at
\texttt{buffer[i \% W]}. Writing a new byte at position $i$ simply overwrites whatever
was at \texttt{buffer[i \% W]} -- the byte from position $i - W$, which has fallen out
of the window and can never be referenced again.
\end{definition}

This gives you $O(W)$ memory for the search buffer, \emph{independent of total file
size} -- exactly the "fixed memory based on parameters I control" property you're
after.

\textbf{Enforcing the window bound in the matchfinder.} Recall
Algorithm~\ref{alg:findmatches}'s hash-chain walk: \texttt{prev[p]} always points to a
\emph{strictly earlier} position, so distance $i - p$ only grows as the chain is
walked. That gives you a free, correct early-exit:
\begin{center}
\textbf{Stop walking the chain the moment $i - p > W$.}
\end{center}
Every remaining entry in the chain is even farther away, hence already outside the
window and unusable -- this is both a correctness requirement (you must never reference
an evicted byte) and a speed win (you stop doing work you'd have to discard anyway). You
never need to explicitly delete old chain entries; capping the walk at distance $> W$
makes them naturally unreachable.

\begin{tcolorbox}[colback=green!5!white,colframe=green!45!black,title={Worked example: watching eviction happen, and how $W$ changes what's even possible}]
Take a deliberately tiny window, $W{=}4$, and trace the ring buffer through our running
example $S = \texttt{abcabcabcxabc}$ (slot $= (i{-}1) \bmod 4$):
\begin{center}
\begin{tabular}{@{}rrrrr@{}}
\toprule
$i$ & byte & slot & buffer contents after write (slots 0--3) & evicted \\
\midrule
1 & a & 0 & a\,\_\,\_\,\_ & -- \\
2 & b & 1 & a\,b\,\_\,\_ & -- \\
3 & c & 2 & a\,b\,c\,\_ & -- \\
4 & a & 3 & a\,b\,c\,a & -- \\
5 & b & 0 & b\,b\,c\,a & byte from $i{=}1$ (\texttt{a}) \\
6 & c & 1 & b\,c\,c\,a & byte from $i{=}2$ (\texttt{b}) \\
7 & a & 2 & b\,c\,a\,a & byte from $i{=}3$ (\texttt{c}) \\
$\vdots$ & & & & \\
11 & a & 2 & \dots & \\
\bottomrule
\end{tabular}
\end{center}
By position 5, the byte written at position 1 is already gone -- overwritten, not just
"old." This is exactly what "fixed memory regardless of file length" costs you: any
match wanting to reference something more than $W$ bytes back simply cannot exist,
because the byte is no longer there to compare against or copy from.

\textbf{Why this makes $W$ a real, consequential choice, not just a memory knob.}
Recall the match found at $i{=}11$ in Section~\ref{sec:matchfinder}: length 3, distance
4 (source position 7). With $W{=}4$, distance $4 \le W$, so this match is still exactly
on the edge of legality -- it survives. With $W{=}3$ instead, distance $4 > W{=}3$, and
this exact match would be \emph{unavailable}: the matchfinder's chain walk would stop
before ever reaching position 7 (Algorithm~\ref{alg:findmatches}'s $i-p \le W$ check),
and the parser would be forced to fall back to literals there instead, costing real bits
(compare $d[13]{=}54$ in Section~\ref{sec:parsing}'s worked table against what it would
become without that match -- strictly worse). This is the concrete mechanism behind
Section~\ref{sec:profiles}'s claim that increasing $W$ can only help or tie the ratio:
a bigger window never removes a match that a smaller one could find, it can only add
matches a smaller window would have missed.
\end{tcolorbox}

\subsection{Why a smaller, fixed window is also \emph{faster}, not just smaller}
\label{sec:cache}

Your instinct that "an algorithm using more memory tends to be slower" is correct, and
it's worth understanding precisely \emph{why}, since it tells you what to tune. The
mechanism is CPU cache locality, not memory quantity per se:

\begin{itemize}
  \item A window/hash-chain structure that fits inside the CPU's L2 or L3 cache (typically
  a few hundred KB to a few tens of MB, depending on hardware) gets match-finding
  lookups served in a handful of cycles.
  \item Once the structure is larger than cache, lookups increasingly miss into main
  memory, each costing on the order of \emph{hundreds} of cycles instead -- a slowdown
  of one to two orders of magnitude per access, not a gentle degradation.
  \item This is exactly why real compressors expose a window/level parameter instead of
  always using the largest window possible: past a certain size, you are trading a
  large, predictable speed cost for a shrinking ratio gain (most of the exploitable
  repetition in typical data lives within a much smaller distance than the theoretical
  maximum).
\end{itemize}

So "fixed, appropriately-sized memory" isn't just easier to reason about -- choosing $W$
to comfortably fit your target cache tier is a legitimate, direct speed lever, separate
from and in addition to \texttt{max\_chain}.

\subsection{Total memory as a function of your own parameters}
\label{sec:memformula}

With window size $W$ and a hash table indexed by $\texttt{hash\_bits}$ bits (so
$2^{\texttt{hash\_bits}}$ buckets):

\begin{center}
\begin{tabular}{@{}p{5.2cm}p{4.3cm}p{4.3cm}@{}}
\toprule
Structure & Size & Notes \\
\midrule
Ring buffer (search buffer data) & $W$ bytes & Section~\ref{sec:ringbuffer} \\
\texttt{head[\,]} (hash $\to$ most recent position) & $4 \cdot 2^{\texttt{hash\_bits}}$ bytes & one \texttt{uint32\_t} per bucket \\
\texttt{prev[\,]} (chain links) & $4 \cdot W$ bytes & one \texttt{uint32\_t} per window position \\
\midrule
\textbf{Total (encoder)} & $W + 4 \cdot 2^{\texttt{hash\_bits}} + 4W$ & $= O(W)$, independent of file size \\
\textbf{Total (decoder)} & $W$ & only the ring buffer -- no hash chain needed at all \\
\bottomrule
\end{tabular}
\end{center}

Note the last row: the \emph{decoder} only ever needs the ring buffer -- decoding is
pure sequential copying (Section~\ref{sec:causality}), never search. All the matchfinder
memory (\texttt{head}, \texttt{prev}) is encoder-only. If you later upgrade to a
binary-tree matchfinder (Section~\ref{sec:matchfinder}), \texttt{prev[\,]} becomes two
child pointers per position instead of one, i.e.\ $8W$ instead of $4W$ -- still $O(W)$,
just a larger constant.

\begin{tcolorbox}[colback=green!5!white,colframe=green!45!black,title=Worked example: memory for a 1MB window]
$W = 2^{20}$ (1{,}048{,}576 bytes), $\texttt{hash\_bits} = 18$ ($262{,}144$ buckets):
\begin{align*}
  \text{ring buffer} &= 1\text{MB} \\
  \texttt{head[\,]} &= 4 \times 262{,}144 = 1\text{MB} \\
  \texttt{prev[\,]} &= 4 \times 1{,}048{,}576 = 4\text{MB} \\
  \textbf{total (encoder)} &\approx 6\text{MB, regardless of whether the input is 1MB or 1GB.}
\end{align*}
The decoder needs only the 1MB ring buffer.
\end{tcolorbox}

\subsection{Parameter profiles: make the speed/ratio/memory trade-off explicit}
\label{sec:profiles}

Rather than picking $W$, \texttt{hash\_bits}, and \texttt{max\_chain} once and hardcoding
them, expose them as named profiles (mirroring how gzip's \texttt{-1..-9}, zstd's
levels, and xz's presets work) so you can dial ratio vs.\ speed without touching code:

\begin{center}
\begin{tabular}{@{}lrrrl@{}}
\toprule
Profile & $W$ & \texttt{hash\_bits} & \texttt{max\_chain} & Encoder memory (approx.) \\
\midrule
Fast & 64~KB & 15 & 32 & $\approx 448$~KB \\
Balanced & 1~MB & 18 & 128 & $\approx 6$~MB \\
Max ratio & 16~MB & 20 & 4096 (or unbounded) & $\approx 68$~MB \\
\bottomrule
\end{tabular}
\end{center}

These are starting points to benchmark from (Section~\ref{sec:validation}), not fixed
recommendations -- the right values depend on your actual data and hardware. The point
is that all three levers ($W$, \texttt{hash\_bits}, \texttt{max\_chain}) are things
\emph{you} set, not properties of the input, which is exactly the "control the
parameters, don't let memory grow with data" property you asked for.

\begin{tcolorbox}[colback=blue!5!white,colframe=blue!50!black,title=Relationship to Section~\ref{sec:calibration}'s "Fast" and "Max ratio" endpoints]
Increasing $W$ can only ever \emph{help or tie} compression ratio (a larger window
means strictly more candidate sources), never hurt it -- so the ratio side of this
trade-off is monotonic. The speed cost is what's non-monotonic (cache locality,
Section~\ref{sec:cache}) and chain-walk cost (\texttt{max\_chain}), which is why these
are worth exposing as explicit, benchmarked profiles rather than a single guess.
\end{tcolorbox}

\section{Match Finding}
\label{sec:matchfinder}

\subsection{Data structure: hash chains}

\begin{definition}[Hash chain matchfinder]
For every position $i$, hash the next $H$ bytes ($H=3$ or $4$ is standard) into a table
\texttt{head[hash]} pointing to the most recent position with that hash, with each
position also storing \texttt{prev[i]} pointing to the next-most-recent earlier position
sharing the same hash -- a singly linked list per hash bucket, walked nearest-first.
\end{definition}

\begin{algorithm}[H]
\caption{Insert position $i$ into the hash-chain structure}
\begin{algorithmic}[1]
\Procedure{InsertPosition}{$i$, $data$, $head[\,]$, $prev[\,]$}
  \State $h \gets \text{Hash}(data[i..i+H-1])$
  \State $prev[i] \gets head[h]$
  \State $head[h] \gets i$
\EndProcedure
\end{algorithmic}
\end{algorithm}

\begin{tcolorbox}[colback=green!5!white,colframe=green!45!black,title={Worked example: building the chain, byte by byte, over $S$}]
Using $H{=}1$ (one byte per hash, as in Section~\ref{sec:matchfinder}'s lookup example)
and inserting every position of $S = \texttt{abcabcabcxabc}$ in order:
\begin{center}
\begin{tabular}{@{}rcrl@{}}
\toprule
$i$ & byte & $prev[i]$ set to & \texttt{head[\,]} after this insert \\
\midrule
1 & a & $-1$ (none yet) & a$\to$1 \\
2 & b & $-1$ & a$\to$1, b$\to$2 \\
3 & c & $-1$ & a$\to$1, b$\to$2, c$\to$3 \\
4 & a & $1$ & a$\to$\textbf{4}, b$\to$2, c$\to$3 \\
5 & b & $2$ & a$\to$4, b$\to$\textbf{5}, c$\to$3 \\
6 & c & $3$ & a$\to$4, b$\to$5, c$\to$\textbf{6} \\
7 & a & $4$ & a$\to$\textbf{7}, b$\to$5, c$\to$6 \\
8 & b & $5$ & a$\to$7, b$\to$\textbf{8}, c$\to$6 \\
9 & c & $6$ & a$\to$7, b$\to$8, c$\to$\textbf{9} \\
10 & x & $-1$ & \dots, x$\to$10 \\
11 & a & $7$ & a$\to$\textbf{11}, \dots \\
12 & b & $8$ & \dots, b$\to$\textbf{12} \\
13 & c & $9$ & \dots, c$\to$\textbf{13} \\
\bottomrule
\end{tabular}
\end{center}
Two things worth noticing directly from the table: (1) \texttt{head['a']} keeps
changing (1 $\to$ 4 $\to$ 7 $\to$ 11) as each new \texttt{'a'} arrives -- it always
holds the \emph{most recent} position, which is exactly what makes nearest-first chain
walking work; (2) $prev[11] = 7$, confirming the lookup traced in the next example: the
chain from position 11 goes straight to 7 (the nearest earlier \texttt{'a'}), then would
continue to 4, then 1, if the walk needed to go further.
\end{tcolorbox}

\begin{algorithm}[H]
\caption{Find match candidates ending at position $l$ (equivalently, starting at $i = l -
s + 1$ for the position under consideration)}
\label{alg:findmatches}
\begin{algorithmic}[1]
\Procedure{FindMatches}{$i$, $data$, $head[\,]$, $prev[\,]$, $max\_chain$, $W$}
  \State $h \gets \text{Hash}(data[i..i+H-1])$
  \State $p \gets head[h]$
  \State $best\_len \gets 0$
  \State $candidates \gets \emptyset$ \Comment{list of (length, distance), one per achievable length}
  \State $tries \gets 0$
  \While{$p \ge 0$ and $tries < max\_chain$ and $i - p \le W$} \Comment{window bound, Section~\ref{sec:ringbuffer}}
    \State $len \gets \text{MatchLength}(data, p, i)$ \Comment{extend while bytes match, capped by window}
    \If{$len > best\_len$}
      \For{$s \gets best\_len+1$ to $len$}
        \State $candidates[s] \gets (s,\, i - p)$ \Comment{nearest distance for every new length reached}
      \EndFor
      \State $best\_len \gets len$
    \EndIf
    \State $p \gets prev[p]$
    \State $tries \gets tries + 1$
  \EndWhile
  \State \textbf{return} $candidates$
\EndProcedure
\end{algorithmic}
\end{algorithm}

\begin{tcolorbox}[colback=blue!5!white,colframe=blue!50!black,title=Key property this relies on]
Because the chain is walked nearest-first, the \emph{first} time a given length is
reached during the walk, its distance is automatically the smallest (cheapest) distance
achieving that length. You never need to compare distances for the same length --
just keep walking until longer matches stop appearing, or the chain/budget runs out.
\end{tcolorbox}

\begin{tcolorbox}[colback=green!5!white,colframe=green!45!black,title=Worked example: two hash-chain lookups on $S$]
Take $H{=}1$ (hash on a single byte, for simplicity of the example only -- real
implementations use $H{=}3$ or $4$ to avoid degenerate chains). As positions $1,2,3$
(\texttt{a},\texttt{b},\texttt{c}) are inserted, \texttt{head['a']}$=1$,
\texttt{head['b']}$=2$, \texttt{head['c']}$=3$.

\textbf{Query at $i=4$} (\texttt{'a'}): $h=$ \texttt{'a'}, $p = head[\texttt{'a'}] = 1$.
\textsc{MatchLength}$(data, 1, 4)$ extends: $S[4]{=}\texttt{a}{=}S[1]$,
$S[5]{=}\texttt{b}{=}S[2]$, $S[6]{=}\texttt{c}{=}S[3]$, $S[7]{=}\texttt{a}{=}S[4]$
(self-overlap, fine), $S[8]{=}\texttt{b}{=}S[5]$, $S[9]{=}\texttt{c}{=}S[6]$,
$S[10]{=}\texttt{x}\ne S[7]{=}\texttt{a}$ -- stop. $len = 6$. $prev[1]$ is empty (no
earlier \texttt{'a'}), so the chain ends after one try. Result: candidates
$(2,3),(3,3),(4,3),(5,3),(6,3)$ -- one entry per length from 2 up to the max found, all
at distance 3 (Section~\ref{sec:candidates} shows exactly this list).

\textbf{Query at $i=11$} (\texttt{'a'}, after \texttt{head['a']} has since been updated
to 7, then to... actually 7 is the most recent \texttt{'a'} before 11, since $i=4$'s
\texttt{'a'} was itself inserted before $i=7$'s): $p = head[\texttt{'a'}] = 7$ (nearest
first, so we try 7 before the older 4 or 1). \textsc{MatchLength}$(data, 7, 11)$:
$S[11]{=}\texttt{a}{=}S[7]$, $S[12]{=}\texttt{b}{=}S[8]$, $S[13]{=}\texttt{c}{=}S[9]$,
end of string -- stop. $len=3$, distance $=11-7=4$. Because the chain is walked
nearest-first, we never even need to check $p=4$ (distance 7) or $p=1$ (distance 10):
both would give the same length-3 match at a needlessly larger distance, hence strictly
more expensive under the cost model in Section~\ref{sec:cost}. Result: candidates
$(2,4),(3,4)$.
\end{tcolorbox}

\subsection{How deep to walk the chain}

\texttt{max\_chain} trades encode speed for match quality. DEFLATE's higher settings use
depths in the hundreds; since your goal is ratio, not encode speed, use a generous depth
(thousands, or unbounded for smaller blocks like your current 64{,}000-byte block size --
exhaustive chain walking on 64KB is entirely affordable on modern hardware).

\subsection{Upgrading the matchfinder later: binary trees and suffix automata}

Hash chains can still miss the best match if the chain is very long and gets truncated by
\texttt{max\_chain}. Two standard upgrades, in order of typical benefit-to-effort:

\begin{itemize}
  \item \textbf{Binary-tree matchfinder} (what LZMA's strongest mode, \texttt{BT4}, uses):
  replace each hash bucket's linked list with a binary search tree ordered by the
  matched suffix, giving exact nearest-distance-per-length without a depth cutoff, at
  $O(\log n)$ insertion/search instead of $O(\text{chain length})$.
  \item \textbf{Suffix automaton / suffix array}: gives you the true longest previous
  factor at every position in one linear-time pass over the whole block, as discussed
  earlier in this project. More work to implement correctly, but removes match-finding
  quality as a variable entirely.
\end{itemize}

Start with hash chains (Algorithm~\ref{alg:findmatches}); it is by far the easiest to get
correct, and with a generous \texttt{max\_chain} on a 64KB block it will already be very
close to exhaustive.

\section{Candidate Representation: Retiring the Old Graph Structure}
\label{sec:candidates}

Your existing \texttt{Graph}/\texttt{GraphNode} machinery enumerates every possible
chunk length $1..k$ at every position (the "virtual parent link" design), because the
old dictionary scheme needed to consider every candidate length to know which ones
repeat anywhere in the file. A real matchfinder does not need this: at each position it
hands you a short, explicit list of \emph{real} candidates.

\begin{definition}[Candidate list]
For each position $l = 1, \dots, n$, define $C_l$ as the list of pairs $(s, \delta)$
returned by \textsc{FindMatches} -- typically a handful of entries, not up to $k=128$.
\end{definition}

\textbf{Recommendation}: replace \texttt{Graph}/\texttt{GraphNode}/\texttt{MAX\_GRAPH\_NODES}
with a flat, per-position array of candidates:
\begin{lstlisting}[language=C]
typedef struct {
    uint32_t length;
    uint32_t distance;
} MatchCandidate;

typedef struct {

\section{Cost Model}
\label{sec:cost}

You already have the right building block: \texttt{lzss\_cost.h}'s
\texttt{lzss\_match\_cost\_bits(length, distance)} and
\texttt{lzss\_literal\_cost\_bits()}. Nothing about this section changes once real
distances are available -- the cost model was already written distance-aware, precisely
in anticipation of this rewrite.

\subsection{What Elias-gamma actually is, as real bits}
\label{sec:eliasgamma}

The formula $\text{var\_cost}(x) = 2\lfloor\log_2 x\rfloor + 1$ isn't an abstract
estimate pulled out of nowhere -- it's the exact bit-length of a real, simple,
self-delimiting binary code for positive integers, called an \emph{Elias-gamma code}.
It's worth seeing what it actually looks like, since "self-delimiting" is doing real
work here: the decoder needs to know where one number's encoding ends and the next
begins, without a separate length field, and this is the mechanism that provides that.

\begin{definition}[Elias-gamma code]
To encode a positive integer $n$: write $n$ in binary, note $k = \lfloor \log_2 n
\rfloor$ (the number of bits \emph{after} the leading 1), then emit $k$ zero bits,
followed by a single $1$ bit, followed by those $k$ remaining bits verbatim. Total
length: $k$ zeros $+$ $1$ bit $+$ $k$ bits $= 2k+1$ bits -- exactly
$\text{var\_cost}(n)$. To decode: count zero bits until the first $1$ (that count is
$k$), then read the next $k$ bits as the remainder $r$; the value is $n = 2^k + r$.
\end{definition}

\begin{tcolorbox}[colback=green!5!white,colframe=green!45!black,title=Worked example: the actual bits for values from our running example]
\begin{center}
\begin{tabular}{@{}rrrl@{}}
\toprule
$n$ & binary of $n$ & $k$ & Elias-gamma code (actual bits) \\
\midrule
1 & 1 & 0 & \texttt{1} (1 bit) \\
3 & 11 & 1 & \texttt{011} (3 bits) -- the distance used in the running example \\
4 & 100 & 2 & \texttt{00100} (5 bits) -- the other running-example distance \\
500 & 111110100 & 8 & \texttt{00000000111110100} (17 bits) -- the "far" option \\
\bottomrule
\end{tabular}
\end{center}
Decoding \texttt{011}: count zeros before the first \texttt{1} $\to$ $k{=}1$; the first
\texttt{1} is the stop marker; read the next $k{=}1$ bit as the remainder, \texttt{1}
$\to r{=}1$; value $= 2^1 + 1 = 3$. Correct, and the decoder never needed to be told in
advance how many bits were coming.
\end{tcolorbox}

\subsection{What it's actually being used for here (and what it isn't)}
\label{sec:eliasgamma-purpose}

This is worth being precise about, since Elias-gamma plays \emph{two conceptually
separate} roles that are easy to blur together:

\begin{enumerate}
  \item \textbf{Its real, current job: a cost estimate for the parser.} The DP in
  Section~\ref{sec:parsing} needs \emph{some} number representing "how expensive is
  this token" in order to compare parses. Elias-gamma is used here \emph{because its
  shape is right} -- cost grows with $\log(\text{value})$, so small distances and short
  lengths are correctly treated as cheap and large ones as expensive -- not because the
  DP is required to actually emit Elias-gamma bits into your compressed file. As
  Section~\ref{sec:entropy} already says, your real entropy coder will very likely beat
  this estimate (an adaptive model over distance \emph{slots}, Section~\ref{sec:slots},
  learns your data's actual distribution instead of assuming this fixed shape) -- that's
  exactly why the iterative refinement loop exists, to keep the DP's decisions aligned
  with whatever your real coder actually costs.
  \item \textbf{An optional, legitimate second job: a real "phase 0" bitstream encoder.}
  Because Elias-gamma is a genuine, complete, working binary code -- not just a cost
  formula -- you can, if you want a fully working end-to-end encoder/decoder before
  building the adaptive range coder in Section~\ref{sec:entropy}, literally write these
  bits to the file (one flag bit per token, then a byte for literals or Elias-gamma-coded
  length/distance for matches). This genuinely saves space compared to fixed-width
  fields (a 3-bit distance costs 3 bits, not a fixed 16 or 32), just not as much as an
  adaptively-modeled coder eventually will.
\end{enumerate}

\begin{tcolorbox}[colback=blue!5!white,colframe=blue!50!black,title={Why building the "phase 0" encoder first is worth doing, not just a shortcut}]
If you implement Elias-gamma \emph{as your real bitstream}, something useful falls out
for free: the DP's predicted cost $d[n]$ (Section~\ref{sec:parsing}) and your actual
compressed file size will match \emph{exactly} (up to rounding to whole bytes) --
because they're now computing the literal same thing. That equality is a strong,
easy correctness check for your matchfinder-plus-DP pipeline (Sections
\ref{sec:matchfinder}--\ref{sec:parsing}) in isolation, \emph{before} the extra
complexity of an adaptive entropy coder is anywhere in the picture. Once that's
verified, swap in the real range coder from Section~\ref{sec:entropy} -- at that point
$d[n]$ becomes an estimate again rather than an exact prediction, and the refinement
loop is what keeps it honest.
\end{tcolorbox}

\begin{tcolorbox}[colback=blue!5!white,colframe=blue!50!black,title=Reminder: why this is exactly the right unit now]
Under the old dictionary/header scheme, a chunk's true cost depended on how many
distinct dictionary entries the whole file ended up needing -- a shared, global,
history-dependent cost the flat DP could not see, which is why the DP lost to greedy in
your benchmark. Under pure back-references, a match's cost is a function of its own
$(length, distance)$ alone, nothing shared with any other token. This is exactly the
assumption the DP's optimality proof requires, so the same DP that lost to greedy
before will not have that problem here.
\end{tcolorbox}

\section{Making Near References Cheaper Than Far Ones: Distance/Length Slots}
\label{sec:slots}

DEFLATE and LZMA both avoid spending a full, uniformly-costed field on every distance:
instead they bucket distances into a small number of \emph{slots} covering
exponentially growing ranges, entropy-code the (small) slot index, and store the
position \emph{within} the slot as close to raw bits as possible, since values within a
bucket are close to equally likely.

\begin{tcolorbox}[colback=blue!5!white,colframe=blue!50!black,title=You already have a version of this -- here's the connection]
\texttt{lzss\_cost.h}'s \texttt{var\_cost}$(x) = 2\lfloor\log_2 x\rfloor + 1$ is already
an Elias-gamma code, and Elias-gamma \emph{is} a slot scheme: it splits $x$ into a slot
index $k = \lfloor \log_2 x \rfloor$ (written in unary, costing $k{+}1$ bits) and $k$
raw extra bits locating $x$ within that slot. So the DP's cost estimates are already
slot-shaped, and nothing here changes how the \emph{parser} reasons about near vs.\ far.
What changes is the \emph{entropy coder}: replacing Elias-gamma's fixed unary slot-index
code with an \emph{adaptively modeled} one, learned from your actual data's distance
distribution, rather than assumed to follow a fixed geometric-ish shape.
\end{tcolorbox}

\begin{definition}[Distance slot]
For a distance $\delta \ge 1$, let $k = \lfloor \log_2 \delta \rfloor$ (the slot index).
Slot $k$ covers the range $[2^k,\, 2^{k+1}-1]$ and needs exactly $k$ extra bits to
specify \emph{which} value in that range: $\text{extra} = \delta - 2^k$. The same
construction applies to match lengths (over a much smaller range, since matches are
typically far shorter than the window).
\end{definition}

\begin{tcolorbox}[colback=green!5!white,colframe=green!45!black,title=Worked example: slotting our running example's distances]
\begin{center}
\begin{tabular}{@{}rrrl@{}}
\toprule
$\delta$ & slot $k$ & extra bits (value) & \\
\midrule
1 & 0 & 0 bits & (smallest possible distance) \\
2 & 1 & 1 bit (value 0) & \\
3 & 1 & 1 bit (value 1) & the distance used in our running example's big match \\
4 & 2 & 2 bits (value 0) & the distance used in our running example's trailing match \\
500 & 8 & 8 bits (value 244) & the "far" option in the greedy-vs-optimal counterexample \\
\bottomrule
\end{tabular}
\end{center}
For a 64KB window, the largest possible distance is 65{,}536, whose slot is $k{=}16$ --
so there are only \textbf{17 distinct slot values} (0 through 16) no matter how large
$\delta$ gets within that window. That's the real payoff: instead of an entropy coder
having to learn a probability distribution over up to 65{,}536 raw distance values, it
only ever needs to learn one over 17 slot values -- small enough to adapt quickly and
cheaply, even early in a file, while the (much larger, but nearly-uniform) extra bits
are left mostly raw, where an adaptive model would buy little anyway.
\end{tcolorbox}

\textbf{Where this belongs in your pipeline}: the slot/extra-bit split itself is a
representation choice for the \emph{entropy coder} (item 3), not the parser -- encode
slot index with an adaptive model (a small frequency table over $\sim$17--20 symbols is
cheap to maintain and converges fast), and write extra bits close to raw (LZMA adds one
adaptively-modeled "aligned" bit per slot on top of raw bits as a small extra refinement;
worth trying once the basic scheme works, not before). Once this real coder exists, feed
its \emph{actual measured} per-slot costs back into the DP through the iterative
refinement loop in Section~\ref{sec:entropy} -- exactly the same loop already in this
guide, just with a better cost source than the Elias-gamma estimate.

\section{Optimal Parsing}
\label{sec:parsing}

\subsection{The flat DP (exactly optimal, given the cost model above)}

This is precisely Section~7 of \texttt{doc/writeup.tex}, restated for candidate lists
instead of graph levels:

\begin{algorithm}[H]
\caption{Optimal parse via forward DP}
\begin{algorithmic}[1]
\Procedure{OptimalParse}{$data$, $candidates[\,]$, $n$}
  \State $d[0] \gets 0$
  \For{$l \gets 1$ to $n$}
    \State $d[l] \gets d[l-1] + \textsc{LiteralCostBits}()$
    \State $back[l] \gets \textsc{Literal}$
    \For{each $(s, \delta) \in candidates[l]$}
      \State $cand \gets d[l - s] + \textsc{MatchCostBits}(s, \delta)$
      \If{$cand < d[l]$}
        \State $d[l] \gets cand$
        \State $back[l] \gets (\textsc{Match}, s, \delta)$
      \EndIf
    \EndFor
  \EndFor
  \State \Return \Call{ReconstructPath}{$back$, $n$}
\EndProcedure
\end{algorithmic}
\end{algorithm}

\textbf{Complexity}: $O(n \cdot \bar{c})$ time, $O(n)$ space, where $\bar{c}$ is the
average candidate-list length (typically small, bounded by \texttt{max\_chain} or by how
many distinct lengths were actually found -- not by $k$). This is the direct successor
of \texttt{shortest\_path\_dp.c}: same forward-sweep structure, simpler inner loop (no
\texttt{get\_parent\_level}/\texttt{useless} bookkeeping needed), same optimality proof.

Feeding the candidate table from Section~\ref{sec:candidates} into

\textbf{Why row 9 is the interesting one.} There are two genuinely different ways to
reach position 9: one big match $(6,3)$ covering positions 4--9 in a single token
($36$ bits total), or two smaller matches -- $(3,3)$ from $i{=}4$ reaching position 6,
then $(3,3)$ again from $i{=}7$ (source $p{=}4$) reaching position 9
($d[6] + \text{match\_cost}(3,3) = 34 + 7 = 41$ bits). The DP correctly rejects the
split (41 bits) in favor of the single long match (36 bits): every extra token pays a
fresh flag bit and a fresh length/distance code, so fragmenting an otherwise-contiguous
match is a real, measurable cost (5 bits here) with no offsetting benefit, since both
pieces would have used the same distance anyway. This is exactly the kind of decision a
greedy "always take what's in front of you" parser gets right by luck when there's only
one source available (as here) -- but not always, as the next example shows.
\end{tcolorbox}

\begin{tcolorbox}[colback=orange!5!white,colframe=orange!70!black,title=Worked counterexample: where plain greedy actually loses]
This one is a constructed synthetic scenario (not from $S$), built specifically to
isolate the failure mode. Suppose at some position, the matchfinder's chain search finds
one long-but-far match: length $7$, distance $500$. Suppose also that, purely by
coincidence, taking just \emph{one literal byte} here and then re-querying the
matchfinder one position later would reveal a match covering the remaining 6 bytes at
distance $4$ (very near) -- but a plain greedy encoder, which only ever asks "what's the
best match available \emph{right now}", cannot see this: it has no mechanism to look
one step ahead and re-evaluate.
\begin{center}
\begin{tabular}{@{}lll@{}}
\toprule
Option & Tokens & Cost \\
\midrule
A (plain greedy's choice) & one match$(7, 500)$ & $1 + \text{var}(6) + \text{var}(500) = 1+5+17 = 23$ bits \\
B (what the DP finds) & literal $+$ match$(6, 4)$ & $9 + (1+\text{var}(5)+\text{var}(4)) = 9+11 = 20$ bits \\
\bottomrule
\end{tabular}
\end{center}
Option B wins by 3 bits, purely because a distance of 4 is so much cheaper to encode than
a distance of 500 that sacrificing one byte of match length more than pays for itself.
Greedy takes Option A because it is the longest match \emph{visible from the current
position} and greedy never reconsiders; the DP in Algorithm~\ref{alg:findmatches}--%
\ref{sec:parsing} naturally finds Option B because $d[\,]$ is computed for
\emph{every} position and compared globally -- it doesn't matter how many steps of
"lookahead" the better option required, since the DP has no lookahead limit at all. Even
DEFLATE's "lazy matching" (which checks only one position ahead) would fail on a version
of this example requiring two or more steps of foresight; the DP has no such bound.
\end{tcolorbox}

\subsection{Extension: repeat-distance modeling (practical, not exactly optimal)}
\label{sec:repdist}

Real data reuses the \emph{same} back-reference distance repeatedly (column-aligned
data, periodic structure). LZMA exploits this with 4 cached "recent distances"
(\texttt{rep0..rep3}); matching one of them costs far fewer bits than encoding a fresh
distance.

\begin{tcolorbox}[colback=red!5!white,colframe=red!60!black,title=Honesty check]
Tracking recent distances exactly turns the DP state into (position, exact set of
recently used distances) -- and distances range up to the window size, so this state
space is not small in general. \emph{Exact} joint optimization of parse and
repeat-distance cache is not tractable this way, and there is no widely known
polynomial algorithm for it in full generality (it is closely related to the "smallest
grammar" family of hard problems flagged earlier in this project). Real encoders,
including LZMA's own optimal-parse mode, do not solve this exactly either -- they use a
bounded-lookahead approximation. What follows is that same standard, practical
approximation, not a new exact algorithm.
\end{tcolorbox}

\textbf{The practical approximation} (what LZMA and zstd's optimal-parse modes actually
do): extend the DP state to $(l, \texttt{rep0})$, where \texttt{rep0} is \emph{only the
single most recently used distance along the best path reaching $l$} (not all four, and
not all combinations) -- carried forward the same way \texttt{shortest\_path\_dp.c}
already carries forward a single winning predecessor per level.

\begin{tcolorbox}[colback=red!5!white,colframe=red!60!black,title={A subtlety to get right: check rep0 at the candidate's own base, not at $l-1$}]
It's tempting to write this as "check whether $rep[l-1]$ still matches something ending
at $l$" -- but that mixes up two different positions' state: $rep[l-1]$ describes the
path arriving at $l-1$, which is not necessarily the same predecessor a given match
candidate at $l$ would use. The correct, internally consistent check is: for a
candidate $(s,\delta)$ ending at $l$ (so its base/predecessor is $l-s$), compare $\delta$
against $rep[l-s]$ -- the rep state at \emph{that specific candidate's own base
position}, not at $l-1$. This way you're always asking "does this candidate happen to
reuse the distance already active at the point it branches from", which is the only
version of the question that is actually well-defined.
\end{tcolorbox}

\begin{algorithm}[H]
\caption{Optimal parse with a single repeat-distance slot (corrected)}
\begin{algorithmic}[1]
\Procedure{OptimalParseWithRep0}{$data$, $candidates[\,]$, $n$}
  \State $d[0] \gets 0$; $rep[0] \gets 0$
  \For{$l \gets 1$ to $n$}
    \State $d[l] \gets d[l-1] + \textsc{LiteralCostBits}()$;\ $back[l] \gets \textsc{Literal}$;\ $rep[l] \gets rep[l-1]$
    \For{each $(s, \delta) \in candidates[l]$}
      \State $base \gets l - s$
      \If{$\delta = rep[base]$ and $rep[base] \ne 0$} \Comment{same distance as active at the base -- reuse it}
        \State $cost \gets \textsc{RepMatchCostBits}(s)$ \Comment{cheaper: no distance field}
      \Else
        \State $cost \gets \textsc{MatchCostBits}(s, \delta)$
      \EndIf
      \State $cand \gets d[base] + cost$
      \If{$cand < d[l]$}
        \State $d[l] \gets cand$;\ $back[l] \gets (\textsc{Match}, s, \delta)$;\ $rep[l] \gets \delta$
      \EndIf
    \EndFor
  \EndFor
  \State \Return \Call{ReconstructPath}{$back$, $n$}
\EndProcedure
\end{algorithmic}
\end{algorithm}

Notice this needs no separate "search for a rep-match" step at all -- it just re-prices
the \emph{same} candidates the matchfinder already found, using whichever cost (fresh or
reuse) is cheaper for each one. That's what keeps it consistent: the rep state and the
DP state now always refer to the same position.

This stays $O(n \cdot \bar{c})$ -- the check is $O(1)$ per existing candidate, nothing
extra to search for -- and typically captures most of the practical benefit of
repeat-distance caching. Extending to 2--4 tracked slots (closer to LZMA's
rep0..rep3) is a straightforward generalization of the same idea if benchmarking shows
it is worth the added complexity; start with one slot and measure before adding more.

\begin{tcolorbox}[colback=green!5!white,colframe=green!45!black,title={Worked example: rep0 genuinely winning, traced in full}]
Take a second short string, purpose-built to actually exercise this (not just a
counterfactual): $T = \texttt{abcabcdefgefg}$ (13 bytes). The matchfinder
(Section~\ref{sec:matchfinder}) finds exactly two real matches here, and -- notice this
carefully -- \emph{both happen to use distance 3}, even though they come from
completely unrelated repeated substrings (\texttt{"abc"} and \texttt{"efg"}):
candidates ending at $l{=}5$ and $l{=}6$ (from \texttt{"abc"} repeating, source
position 1), and at $l{=}12$ and $l{=}13$ (from \texttt{"efg"} repeating, source
position 8).
\begin{center}
\begin{tabular}{@{}rrp{9.5cm}@{}}
\toprule
$l$ & $d[l]$ (bits) & chosen edge \\
\midrule
0--4 & $0,9,18,27,36$ & literals (unchanged from the plain-DP pattern) \\
5 & 32 & fresh match$(2,3)$ from $d[3]{=}27$; $rep[5]{\gets}3$ \\
6 & 34 & fresh match$(3,3)$ from $d[3]{=}27$ ($rep[3]{=}0$, so no reuse yet); $rep[6]{\gets}3$ \\
7--10 & $43,52,61,70$ & literals (\texttt{d},\texttt{e},\texttt{f},\texttt{g}); $rep$ stays 3 throughout \\

\textbf{Final cost: 74 bits.} Re-running the exact same candidates through the

the second match's distance (3) was charged fresh instead of recognized as a reuse of
what was already active. This is a real, verified improvement, not a counterfactual --
and it demonstrates the honest, ordinary case: rep0 helps precisely when two
\emph{unrelated} repeats happen to sit the same distance apart, which is common in
structured or periodic data and exactly why Section~\ref{sec:calibration} flags this as
often the best ratio-per-effort item on the whole roadmap.
\end{tcolorbox}

\section{Entropy Coding Integration}
\label{sec:entropy}

Your plan (item 3: range coding / context mixing) is already the right choice --
strictly more expressive than DEFLATE's Huffman stage, which is limited to integer-bit
code lengths per symbol.

\subsection{The cost-model / entropy-coder feedback loop}

The bit costs in Section~\ref{sec:cost} are \emph{estimates} (an Elias-gamma-style
approximation), not what your adaptive entropy coder will actually spend, since its
costs depend on model state that evolves with the actual token sequence chosen. The
standard, well-tested resolution (used by LZMA/zstd) is iterative:

\begin{enumerate}
  \item Parse once using the static cost estimates from Section~\ref{sec:cost}.
  \item Feed the resulting token sequence through the real entropy coder; measure the
  actual bits it assigned to each literal/length/distance symbol.
  \item Re-derive per-symbol cost estimates from those measured statistics.
  \item Re-run \textsc{OptimalParse} (Section~\ref{sec:parsing}) with the updated costs.
  \item Repeat 2--4 rounds, or until total size stops improving.
\end{enumerate}

This is not a proof of global optimality (exact joint optimization of parse and adaptive
model state is intractable in general, for the same reason as
Section~\ref{sec:repdist}) -- but it is an empirically excellent fixed point, and it is
exactly what today's best general-purpose compressors ship.

\begin{tcolorbox}[colback=orange!5!white,colframe=orange!70!black,title={Illustrative example (hypothetical numbers -- not measured, unlike every other worked example in this document)}]
Every other numeric example in this guide was computed by script and is exact. This one
isn't, because it depends on a real entropy coder that doesn't exist yet -- it's here
only to make the \emph{mechanism} concrete, not to predict actual numbers.

\textbf{Round 1}: parse $S$ using the static Elias-gamma estimates, exactly as in
Section~\ref{sec:parsing} -- literals \texttt{a},\texttt{b},\texttt{c} at 9 bits each,
match$(6,3)$ at 9 bits, literal \texttt{x} at 9 bits, match$(3,4)$ at 9 bits, total 54
bits (this part is the real, verified number from Section~\ref{sec:parsing}).

\textbf{Measure}: feed this exact token sequence through a real adaptive entropy coder.
Suppose (hypothetically) it discovers that \texttt{a}, \texttt{b}, \texttt{c} are
common in this file and assigns them only $\sim$4 bits each once it has adapted, while
rare \texttt{x} still costs close to 9 bits, and the two match tokens measure at 8 and
10 bits respectively (slightly different from the 9-bit Elias-gamma guess in each
direction, since the real coder's length/distance-slot model, Section~\ref{sec:slots},
doesn't match Elias-gamma's assumed shape exactly). Measured total: $4{+}4{+}4{+}8{+}9{+}10 = 39$ bits
-- already better than the estimate suggested, just from better entropy coding of the
\emph{same} parse.

\textbf{Re-price and re-parse}: feed these \emph{measured} per-symbol costs back into
\textsc{OptimalParse} instead of the Elias-gamma estimates. If, under these updated
costs, some other combination of tokens (e.g.\ a different split point, or trading a
match for literals that are now unexpectedly cheap) totals fewer bits than 39, the DP
will find and switch to it -- this is the case where round 2 changes the actual parse,
not just its measured cost. Repeat measure/re-parse for 2--4 rounds, or until the total
stops improving.
\end{tcolorbox}

\subsection{Context choices for the entropy stage, roughly in order of expected payoff}

\begin{enumerate}
  \item Separate probability models for literals vs.\ match-length vs.\ distance
  symbols (do not share one model across all three).
  \item Condition literal probabilities on the preceding 1--2 bytes (order-1/order-2
  context), not just an unconditional byte frequency table.
  \item Condition on whether the previous token was a literal or a match (DEFLATE and
  LZMA both find this genuinely useful).
  \item If you pursue full context mixing: combine several such predictors with a
  logistic mixer (PAQ/cmix-style) rather than picking one context order -- this is where
  most of the ratio gap to state-of-the-art compressors actually lives, more so than in
  parsing sophistication.
\end{enumerate}

\section{Validation and Benchmarking Protocol}
\label{sec:validation}

\begin{enumerate}
  \item \textbf{Correctness first, always}: every change gets a full round-trip
  (compress $\to$ decompress $\to$ byte-diff) over your entire \texttt{tests/} corpus,
  including \texttt{tests/cantrbry}, before you look at compression ratio at all.
  \item \textbf{Compare against real baselines on the same files}: \texttt{gzip -9},
  \texttt{zstd --ultra -22}, and \texttt{xz -9e} on every test file, not just your
  previous version -- your own history-vs-history comparisons (DP vs.\ greedy) are
  useful for internal regressions, but the external baselines are what tells you whether
  you are actually competitive.
  \item \textbf{Ablate one change at a time}: matchfinder quality, DP vs.\ greedy,
  rep-distance, entropy stage -- toggle each independently so you know which one is
  actually earning its keep, the same way this document's earlier greedy-vs-DP
  benchmark isolated exactly one variable.
  \item \textbf{Track encode time too}: an exhaustive \texttt{max\_chain} and a full
  context-mixing entropy stage can get slow; note the trade-off even if ratio is your
  primary goal, so you know what you're spending to get it.
\end{enumerate}

\section{Calibration: Where the Real Gains Actually Come From}
\label{sec:calibration}

Read this section before writing code, not after.

\begin{enumerate}
  \item \textbf{Matchfinder quality} (Section~\ref{sec:matchfinder}): a shallow hash
  chain vs.\ an exhaustive one, or vs.\ a binary tree, changes what matches you can even
  see. Real, but bounded, gains.
  \item \textbf{Optimal vs.\ greedy parsing} (Section~\ref{sec:parsing}): you already
  measured this empirically on your own data once the cost model is fair (see the
  earlier greedy-vs-DP benchmark in this project) -- meaningful, but this alone will
  bring you roughly to where LZMA/zstd's own optimal-parse modes already are, not past
  them, since they do this too.
  \item \textbf{Repeat-distance modeling} (Section~\ref{sec:repdist}): often the single
  best ratio-per-effort win on structured/periodic data, and a real point of leverage
  over compressors that skip it.
  \item \textbf{Entropy coding sophistication} (Section~\ref{sec:entropy}): once parsing
  is near-optimal, this is realistically where most of the remaining gap to
  state-of-the-art ratios lives -- how well you predict the next symbol's probability,
  not how you choose chunk boundaries. The very best general-purpose compressors (cmix,
  paq-family) get their ratio almost entirely from rich, mixed context models here, not
  from unusual match-finding.
\end{enumerate}

\begin{tcolorbox}[colback=yellow!5!white,colframe=yellow!75!black,title=Honest expectation setting]
Beating gzip/DEFLATE outright is a realistic, achievable target with just
Sections~\ref{sec:matchfinder}--\ref{sec:parsing} (better matchfinder + optimal parse
already exceeds DEFLATE's greedy/lazy design). Matching or narrowly beating zstd at high
levels and competing with LZMA/xz is achievable but will require Sections
\ref{sec:repdist}--\ref{sec:entropy} done well, since those tools already run
near-optimal parsers themselves -- your edge over them has to come from matching or
exceeding their entropy-coding sophistication, not from parsing alone. Decisively
beating LZMA/zstd/xz \emph{in general}, across all data types, is a very high bar few
tools clear; beating them on a \emph{specific} data type you care about (by exploiting
structure they don't model) is a much more tractable and still valuable goal. Aim
there first.
\end{tcolorbox}
